TITLE|在线学习平台系统设计与实现

H1|1 系统分析
H2|1.1 问题说明
H3|1.1.1 项目背景
P|随着互联网技术与教育信息化的深度融合，在线学习已经成为高校教学体系中不可或缺的组成部分。传统的课堂教学在时间与空间上受到较大限制：学生课后缺乏系统的复习载体，教师难以掌握每位学生的学习进度，纸质作业的收发与批阅效率低下，测验的组卷、判分与成绩统计更是占用教师大量时间。虽然在慕课平台上已经出现了大量优质课程资源，但面向本校教学场景、支持教师自主建课并覆盖"建课—选课—学习—测验—批阅—反馈"完整教学闭环的轻量级平台仍然有明确的现实需求。
P|本实训课题选择"在线学习平台系统设计与实现"作为题目，正是基于上述背景。课题要求综合运用软件工程、数据库原理、Java Web 开发、前端工程化等课程所学知识，独立完成一个真实可运行的 Web 应用系统的分析、设计、实现与测试，在实践中体会软件工程的完整生命周期。
H3|1.1.2 系统建设目标
P|本系统的建设目标是：面向高校教学场景，构建一个支持学生、教师、管理员三种角色，覆盖课程发布、选课学习、随堂测验、作业批阅、学情统计、讨论互动等核心教学环节的在线学习平台。系统应当做到功能完整、职责清晰、数据一致、安全可控，并具备良好的可维护性与可扩展性，为后续迭代（如引入缓存中间件、对象存储、消息队列等）预留空间。
P|具体而言，系统需要达成以下目标：（1）教师可以自主创建课程并组织章节内容，上传课件与教学视频，维护题库、组建试卷、布置作业，并通过学情看板掌握班级整体学习情况；（2）学生可以浏览课程广场、选课学习、完成章节打卡、参加在线测验、提交作业、参与讨论、记录学习笔记，并随时查看自己的成绩与学习进度；（3）管理员负责平台级的治理工作，包括用户管理、课程审核、分类维护、公告发布与平台数据统计；（4）课程从创建到对学生可见必须经过审核流程，保证平台内容质量可控。
H3|1.1.3 系统边界与运行环境
P|本系统为 B/S 架构的 Web 应用，运行于局域网或互联网环境。服务器端运行环境为 Windows 或 Linux 操作系统，依赖 JDK 17 运行时与 MySQL 9.2 数据库服务；客户端为现代桌面浏览器（Chrome、Edge 等），无需安装任何插件。文件资源（课件、视频、头像等）在当前版本存储于服务器本地磁盘的 upload 目录下，接口设计上做了存储抽象，后续可平滑迁移至 MinIO 或云对象存储。系统提供 docker-compose.yml 编排文件，支持一键容器化部署，便于演示与验收。

P|在数据需求的粒度上，本阶段同步建立了初步的数据字典思想：为每一类数据约定了命名风格（数据库字段小写下划线、Java 属性小驼峰）、主键策略（统一 BIGINT 自增）、时间字段规范（统一 DATETIME、数据库默认值 CURRENT_TIMESTAMP）、状态字段规范（统一 TINYINT 并在字段注释中枚举全部取值含义）。统一的数据规范在后续 20 张表的实施过程中避免了风格漂移，也使得实体类与数据表之间可以保持几乎机械的对应关系，显著降低了持久层代码的编写与排查成本。

H3|1.3.2 学生端功能需求
P|学生端是系统面向学习者的大门，其功能需求围绕"找到课、学下去、考出来、有反馈"四个环节展开。（1）课程浏览与检索：课程广场按分类与热度展示已发布课程，支持关键词搜索与分类筛选，未登录用户可以游客身份查看课程列表与详情；（2）选课管理：学生对感兴趣的课程发起选课，若课程开启了选课审核，则进入待审核状态，由教师审批；支持退课与课程收藏；（3）在线学习：进入学习页后按章节顺序观看视频、阅读图文、查看课件，学完后打卡标记，系统实时统计课程完成率；（4）在线测验：在试卷允许的时间窗口内进入答题，支持单选、多选、判断、填空、问答五种题型，交卷后客观题即时出分并展示逐题解析，问答题由教师批阅；（5）作业管理：查看课程作业要求，在截止时间前以富文本加附件的形式提交，一次作答机会，提交后可查看教师批阅结果与评语，支持导出作业与试卷用于线下复习；（6）辅助功能：学习笔记（支持富文本与粘贴插图）、讨论区发帖回帖与"有帮助"标记、个人中心资料维护、成绩汇总查询。
H3|1.3.3 教师端功能需求
P|教师端的功能需求围绕课程全生命周期管理展开。（1）课程管理：创建课程（草稿）、编辑课程信息、设置选课是否需要审核、课件是否允许下载、资料导出范围等课程级开关，提交审核后等待管理员放行；（2）章节管理：维护章节顺序，上传章节视频与课件资源，编辑图文讲义；（3）题库管理：维护本课程的题目，支持五种题型，支持通过 Excel 模板批量导入与导出；（4）试卷管理：从题库选题组卷，设置每题分值、总分、及格分、考试时长与开放时间窗，发布后学生可见，重新发布自动递增版本号并使旧答卷失效；（5）作业管理：布置作业并附模板附件，设定截止时间，批阅学生提交，打分并给出评语；（6）学情管理：查看课程学生名单，审批选课申请，按登录名批量导入学生，通过学情看板查看选课人数、完成率、测验通过率等统计指标，查看每份答卷并改分。
H3|1.3.4 管理端功能需求
P|管理端承担平台治理职能。（1）用户管理：分页查询用户、启用/禁用账号、调整角色，支持按 CSV 模板批量导入用户并逐行返回导入结果；（2）课程审核：查看待审核课程列表，审核通过后课程对学生可见，驳回时须填写驳回理由并反馈给教师；（3）分类管理：维护两级课程分类及其排序；（4）公告管理：发布、置顶、撤下平台公告；（5）平台统计：汇总用户数、课程数、选课人次等核心指标，以图表形式直观展示平台运行状况。

H1|2 系统设计
H2|2.1 总体设计
H3|2.1.1 设计原则
P|系统总体设计遵循以下原则：（1）前后端分离，前端与后端仅通过 RESTful API 通信，双方以 JSON 报文交互，接口契约先行，便于独立开发、独立部署与后续多端复用；（2）分层解耦，后端严格划分为控制层、业务层、持久层，各层职责单一、自上而下单向依赖；（3）约定优于配置，统一响应体、统一异常处理、统一命名风格，降低协作与维护成本；（4）安全内建，认证与鉴权在框架层（拦截器+注解）统一解决，业务代码不重复处理权限逻辑；（5）渐进演进，文件存储、缓存等组件预留替换空间，不为实训环境过度设计。
H3|2.1.2 系统总体架构
P|系统采用"Vue 3 前端 + Spring Boot 后端 + MySQL 数据库"的前后端分离三层架构，总体架构如图2-1所示。浏览器中的 Vue 3 单页应用通过 Axios 发起 HTTPS 请求，请求先经过后端 JWT 拦截器完成认证与鉴权，再由控制层路由到对应业务服务，业务层经 MyBatis-Plus 访问 MySQL 数据库；文件类请求由独立的文件控制器处理，直接读写服务器本地磁盘。前端开发期由 Vite 开发服务器承载，生产构建产物由 Nginx 或容器直接托管。

P|后端按功能分包组织，架构如图2-3所示。controller 包按访问身份划分为认证、公开接口、学生、教师、管理、文件六组控制器；service 包承载全部业务规则；mapper 包基于 MyBatis-Plus 提供数据访问；entity 与 dto 包分别承载数据表映射对象与请求/响应对象；common 包提供统一响应体 Result、业务异常 BusinessException 与全局异常处理器；security 包实现 JWT 工具、认证拦截器、角色注解与用户上下文；config 包完成跨域、拦截器注册、MyBatis-Plus 分页插件与接口文档配置。

P|请求处理链路为：HTTP 请求 → 跨域与 JWT 拦截器（认证、写入用户上下文、校验 @RequireRole 注解）→ 控制器（参数校验、调用服务）→ 业务服务（业务规则、事务控制）→ Mapper（数据持久化）→ 统一响应体返回。任何位置抛出的业务异常均由全局异常处理器兜底转换为规范的错误响应，保证前端收到的报文结构始终一致。

H3|2.2.3 数据库实施要点
P|数据库初始化脚本 init.sql 完成建库、建表与演示数据写入，脚本可重复执行（先 DROP 再 CREATE）。考虑到功能迭代需要修改表结构，系统配套提供了 upgrade-v3.sql 与 upgrade-v4.sql 两个幂等升级脚本：脚本内部通过判断列、索引是否已存在来决定是否执行变更，因此在任意版本的旧库上重复执行均能安全收敛到目标结构，避免"换个环境就重建库"的低级做法。执行时统一指定 --default-character-set=utf8mb4，防止存储过程中的中文注释因字符集不一致而报错。
H2|2.3 输入/输出设计
H3|2.3.1 输入设计
P|系统的输入包括结构化表单输入、富文本输入与文件输入三类。表单输入（登录、注册、建课、组卷等）在前端使用 Element Plus 表单校验规则做第一道把关（必填、长度、格式），在后端再做参数合法性校验，两端规则保持一致；用户名长度限定 4~20 位字母数字下划线，批量导入时逐行校验并逐行反馈成功或失败原因，失败原因精确到"第几行、哪个字段、什么原因"。富文本输入（作业作答、学习笔记、问答题）使用自制富文本编辑器，支持常用排版与粘贴剪贴板图片，粘贴的图片自动上传后以 img 标签插入正文。文件输入统一走文件上传组件，前端限制文件类型与大小，后端对文件名做规范化处理并重新命名存储，杜绝路径拼接类风险。
H3|2.3.2 输出设计
P|系统的输出包括页面数据、文件与报表三类。（1）页面数据统一采用 Result{code, message, data} 响应结构，分页查询统一返回 {records, total, current, size} 分页结构，前端据此做统一的 loading、错误提示与分页处理；（2）文件输出包括课件在线预览（后端解析为结构化内容，前端渲染）与原文件下载（受课程 resource_downloadable 开关控制）；（3）报表输出支持将试卷、作业及学生作答导出为 Word 文档，导出范围由课程 export_scope 开关控制（关闭、仅选课学生、全部用户三档），题库支持 Excel 导入导出，便于教师离线备课与跨课程复题。
H2|2.4 安全性设计
H3|2.4.1 认证与授权设计
P|系统采用 JWT 无状态认证与基于注解的角色鉴权。登录成功后服务端签发 JWT，前端将其存入本地并在后续请求的 Authorization 头中携带；后端拦截器统一解析 token，将用户信息写入 ThreadLocal 用户上下文，业务代码通过上下文直接获取当前用户；控制器类或方法上以 @RequireRole 注解声明所需角色，拦截器比对后决定放行或拒绝，越权返回 403，未登录返回 401。认证与授权的完整时序如图2-6所示。

P|针对两类特殊场景做了专门设计：其一，浏览器直接打开附件（如 window.open 下载）时无法携带请求头，拦截器支持以查询参数 token 兜底；其二，公开接口采取"尽力解析"策略——携带合法 token 时将用户写入上下文，使课程详情等接口能返回"是否已选课、学习进度"等个性化字段，未登录时则退化为游客视图而非直接拒绝，兼顾安全与体验。
H3|2.4.2 密码存储与防作弊设计
P|密码采用"MD5 + 随机盐"方案存储，盐值逐用户随机生成并与密文一同落库，即使数据库泄露攻击者也难以通过彩虹表直接反查明文（生产环境建议升级为 BCrypt 等自适应慢哈希，本设计按实训要求采用 MD5 加盐）。防作弊设计体现在三处：（1）学生端拉取试卷时，服务端剔除 answer 与 analysis 字段，答案永不前置下发；（2）测验与作业仅允许提交一次，Service 层在事务内校验历史记录，前端"已提交即只读"仅为体验优化；（3）试卷发布版本机制保证教师改卷重新发布后，旧答卷不能沿用，防止利用历史答卷重复得分。

H3|2.5.3 作业与讨论模块设计
P|作业模块与测验模块同属考核域，但业务形态差异明显：作业无标准答案，以"要求—作答—批阅"的人工流转为主。设计上，作业表通过 chapter_id 支持挂靠到具体章节，requirement 字段采用富文本承载图文并茂的作业要求，attach_url 支持下发附件模板（如代码框架、文档模板）；提交表以 (assignment_id, user_id) 唯一约束实现"仅一次提交"，教师批阅后写入 score 与 comment，status 由"待批阅"翻转为"已批阅"。v4 迭代进一步为作业与测验引入了作答时间窗：作业以 start_time 与 deadline 构成窗口，试卷以 start_time 与 end_time 构成窗口，窗口校验在前端提示、后端 checkWindow 兜底，两端任一被绕过都无法突破时间限制。
P|讨论模块围绕帖子组织：帖子挂在课程下，回复直接线性跟随帖子，"有帮助"以独立关联表去重，避免在帖子表上用计数器难以防重的缺陷。讨论帖与回复均设计软删除位，删除操作只改状态不物理清除，保证教学场景下交流数据的可追溯。学习笔记则支持挂靠课程或章节两级，并可在作答或学习过程中随时唤起，形成"边学边记"的闭环；笔记与作业、测验的关联通过 ref_type 与 ref_id 两个多态引用字段实现，使一份笔记可以指向一份作业或一份试卷，减少重复记录。
H2|2.6 用户界面设计
H3|2.6.1 设计风格与规范
P|界面整体采用"暖米橙"视觉风格：底色使用暖米白（#fdf7f1），主色为活力橙（#ff6b35），辅以浅色卡片与柔和圆角，营造亲和、专注的学习氛围。设计执行三条硬性规范：（1）设计令牌单一来源，全部颜色、字体、圆角集中定义于 theme.css，页面不写裸色值，保证跨页面视觉一致；（2）弹窗与抽屉一律挂载到 body，避免被父容器层叠上下文裁剪；（3）学员端图表以轻量 SVG 手绘为主、教师与管理端使用 ECharts，配色统一取自主题色板。课程封面按课程 ID 取固定渐变色，保证同一课程在各页面的观感一致。

H3|2.6.3 交互容错与细节设计
P|除静态布局外，界面设计还约定了一批交互容错规则：（1）破坏性操作（退课、删题、撤卷）一律二次确认，确认文案明确说明后果；（2）表单提交按钮在请求期间置为加载态，防止重复点击造成重复提交；（3）列表类页面在数据为空时展示空状态与引导文案，而非一片空白；（4）所有错误提示使用统一的消息组件，文案区分"系统错误"与"业务拒绝"两类语气，避免把技术细节暴露给最终用户；（5）长时间任务（批量导入、文件上传）必须给出进度或逐条结果反馈，不允许"点了没反应"。这些规则在测试阶段被证明有效拦截了大量误操作类缺陷。

H3|3.2.1 JWT 认证与角色鉴权
P|认证拦截器 JwtInterceptor 在 preHandle 中完成三件事：放行预检请求、解析 token 并写入用户上下文、校验 @RequireRole 角色注解。关键实现如下：
CODE|// 关键片段：token 解析与角色校验
CODE|if (!StringUtils.hasText(header) || !header.startsWith("Bearer ")) {
CODE|    throw new BusinessException(401, "未登录或登录已过期，请重新登录");
CODE|}
CODE|Claims claims = jwtUtil.parse(header.substring(7));
CODE|UserContext.set(new UserContext.User(claims.get("userId", Long.class),
CODE|        claims.get("role", String.class)));
CODE|RequireRole anno = handlerMethod.getMethodAnnotation(RequireRole.class);
CODE|if (anno == null) anno = handlerMethod.getBeanType().getAnnotation(RequireRole.class);
CODE|if (anno != null && !Arrays.asList(anno.value()).contains(UserContext.get().role())) {
CODE|    throw new BusinessException(403, "没有访问权限");
CODE|}
P|该实现将认证与鉴权收敛在框架层，控制器只需按需标注 @RequireRole("TEACHER") 即可声明权限，业务代码零侵入。请求结束后在 afterCompletion 中清理 ThreadLocal，防止线程复用导致的用户串号。
H3|3.2.2 在线测验自动判分
P|交卷判分是全系统最核心的业务方法，实现在 ExamService.submit 中，方法整体置于事务内，关键判分逻辑如下：

CODE|    if (type == TYPE_ESSAY) {          // 问答题：留给教师批阅
CODE|        hasEssay = true;
CODE|        detail.setNeedManual(true);

CODE|        boolean correct = isCorrect(q, your);

CODE|record.setMarkStatus(hasEssay ? 1 : 0);  // 有问答题 → 待批阅

H3|3.2.4 课件在线预览
P|DocPreviewService 依据文件扩展名分发到不同解析器：PDF 直接返回原始地址交给前端 iframe；docx 使用 XWPF 逐段抽取文本与表格；pptx 使用 XMLSlideShow 逐页解析，页面内嵌图片转 base64 一并返回；xlsx 使用 XSSF 按工作表抽取；旧版二进制格式 doc/ppt/xls 降级由 poi-scratchpad 的 HWPF/HSLF/HSSF 处理。解析结果统一组织为"块"列表返回，前端 FilePreview 组件按块类型渲染，pptx 附带全屏放映模式。该方案不依赖 LibreOffice 等外部进程，部署简单、响应快，代价是对 SmartArt、公式等复杂版式不保证完全还原，已在系统约束中如实注明。
H3|3.2.5 文件上传与权限控制
P|文件上传统一收敛到 FileUploader 组件与 FileService：前端组件统一处理类型校验、进度展示与回显；后端为每个文件生成新的存储名，按业务目录归类存放于 upload 目录，返回相对 URL。下载与预览经由公共文件控制器统一寻址（支持资源 ID 与 URL 双寻址），下载前校验目标课程的 resource_downloadable 开关，关闭时返回 403；资料导出（试卷、作业转 Word）受 export_scope 三档控制，未授权用户请求导出直接拒绝。
H3|3.2.6 学情统计与成绩汇总
P|学情统计是教师调整教学策略的依据，实现上采用"聚合查询 + 前端可视化"的组合。教师端学情看板在一次请求内聚合多项指标：课程总数、选课总人数、作业待批阅数、测验待批阅数，以及按课程维度的平均完成率与测验通过率；管理端平台统计则汇总用户规模、课程规模与选课规模。聚合查询全部使用 SQL 的条件计数完成，避免在应用层循环查询造成 N+1 问题。学生侧的"我的成绩"页面按课程汇总作业得分与测验记录，测验记录附带走 paper_version 信息，使学生回看历史成绩时能明确区分当前版本答卷与已作废答卷。
H3|3.2.7 题库批量导入导出
P|为方便教师离线备课，题库支持 Excel 批量导入导出。导出使用 Apache POI 生成工作簿，表头固定为"题型、题干、选项A~F、答案、参考答案、解析、难度"，并为模板附加"填写说明"工作页，逐项说明五种题型的填法（如填空题多空用竖线分隔、同空多写法用波浪线分隔、多选题答案用英文逗号连接选项字母）。导入时逐行解析并校验：题型必须是合法枚举、客观题答案不得为空、选项数量与题型匹配、难度取值合法；校验失败的行不中断整体流程，而是逐行记录失败原因，全部处理完毕后一次性返回"成功 N 行、失败 M 行"及每行的失败详情，教师修正后可重新导入。

H2|4.4 AI使用效果与反思
P|总体来看，AI 辅助在"缩短资料检索时间、提供第二视角"方面有可量化的收益：例如快速澄清了 jjwt 0.12 版本 API 的变更点、MySQL 9 默认排序规则与旧客户端的兼容坑位，预计节省了查阅官方文档的时间。但过程中也暴露出 AI 输出的典型局限：其生成的代码片段常隐含与本项目不一致的假设（如字段命名、错误码、事务边界），若不加审查直接采用会引入风格割裂甚至隐蔽缺陷；个别回答存在版本混淆，需要本人交叉验证。这段经历使我认识到：AI 是放大执行效率的工具，而需求理解、架构权衡与质量责任始终属于开发者本人，审慎、批判地使用 AI 是未来软件工程素养的必要组成部分。
P|从协作过程的数据看，本项目全部代码提交均由本人完成并逐次审查，AI 参与产生的最终采纳代码集中在异常类、响应体等样板性质的部分，核心业务包（测验判分、权限拦截、预览解析）无任何整体生成代码。使用 AI 的时段也呈现明显的场景分布：集中在项目初期技术调研与末期文档整理两个阶段，编码高峰期的交流反而最少，这与"AI 辅助思考、人来负责实现"的定位是吻合的。若以一句话概括本次人机协作的经验，那就是：把 AI 当作一位随叫随到的讨论伙伴，而不是一位代笔者；提问越具体、验证越严格，协作的质量就越高。

H1|5 实训总结
H2|5.1 设计的特点
P|回顾整个设计过程，本系统具有以下特点：（1）业务闭环完整，覆盖"建课—审核—选课—学习—测验—批阅—统计"教学全流程，不是功能点的简单堆砌，而是围绕真实教学场景组织的有机整体；（2）权限与安全设计贯穿始终，JWT 认证、注解式鉴权、答案不下发、一次性提交、时间窗控制、下载与导出开关等多层约束前后端双重生效；（3）数据一致性强，关键业务约束以唯一索引落库兜底，试卷版本化机制妥善解决了"改卷"与"历史答卷"的矛盾；（4）体验细节扎实，草稿自动保存、课件全格式预览与 PPT 放映、富文本粘贴插图等细节显著提升了可用性；（5）工程化程度高，幂等数据库升级脚本、可重复执行的冒烟测试、统一响应体与全局异常处理等实践保证了系统的可维护性。
H2|5.2 遇到的主要问题与解决
P|开发过程中遇到并解决的代表性问题包括：（1）MySQL 9 排序规则问题：新库默认使用 utf8mb4_0900_ai_ci，旧客户端连接时出现字符集报错，通过统一客户端 utf8mb4 参数并明确库级排序规则解决；（2）Maven 命令兼容问题：Git Bash 环境下直接调用 mvn 报 classworlds 异常，改用 mvn.cmd 后恢复，由此形成了本机的构建命令约定；（3）Element Plus 弹窗被遮挡：部分弹窗出现在父容器层叠上下文之下导致交互失效，定位到 append-to-body 缺失后，全站 13 处弹窗统一修复并沉淀为组件规范；（4）个人中心头像被装饰带遮挡：通过显式管理 z-index 层级解决，再次验证了层叠上下文知识在实战中的价值；（5）课件预览的格式覆盖：初版仅支持 OOXML 格式，为覆盖旧版二进制文档引入 poi-scratchpad，在"纯 Java 解析"与"格式覆盖面"之间做了务实的取舍并如实注明边界。这些问题的解决过程让我体会到，工程能力的核心不在于不遇到问题，而在于遇到问题后系统性的定位方法与沉淀习惯。
H2|5.3 收获与体会
P|三周实训是我第一次完整地走通一个 Web 系统从需求到验收的全过程，收获远超预期。技术层面，我真正掌握了 Spring Boot 3 与 Vue 3 的工程化用法，理解了拦截器、事务、ThreadLocal 上下文、唯一约束兜底等机制在真实业务中的落地方式，也第一次认真思考"版本号""幂等""可重复执行的脚本"这类工程品质的必要性。方法论层面，我深刻体会到"先设计后编码"的价值：ER 图上多花一小时，建表阶段就少返工半天；测试先行意识的建立，让冒烟脚本成为后续每次改动的安全网。素养层面，AI 协作的实践让我建立了对 AI 输出的批判性使用习惯，明白效率工具无法替代开发者对系统的理解与责任。此外，撰写本报告的过程也训练了我规范表达技术方案的能力，这本身就是软件工程师的核心技能之一。
